# Dense baseline trace: generation and use

This archive contains a synthetic dense-transformer pretraining workload for **32 simulated accelerators**. You can extract it into any directory. The directory name is not part of the trace configuration.

## Contents

- `dense32_validmb.0.et` through `dense32_validmb.31.et`: one Chakra execution trace per accelerator rank.
- `dense32_validmb.json`: communicator membership for collective operations in the trace. This is **not** a physical network topology.
- `SHA256SUMS`: checksums for the 33 trace files.
- `instructions.md`: this document.

Use the included files when you need every teammate to simulate **exactly the same workload**. Regeneration instructions follow so you can audit or extend it.

## Exact workload parameters

| Parameter | Value | Meaning |
| --- | ---: | --- |
| `--model_type` | `dense` | Dense transformer; no routed experts. |
| `--dp` | `8` | Eight data-parallel replicas. |
| `--tp` | `4` | Each replica uses four tensor-parallel ranks. |
| `--ep`, `--pp`, `--sp` | `1`, `1`, `1` | No expert, pipeline, or sequence parallelism. |
| `--batch` | `32` | Global batch of 32 sequences. |
| `--micro_batch` | `8` | Four global microbatches; one sequence per DP replica per microbatch. |
| `--seq` | `512` | Tokens per sequence. |
| `--dmodel`, `--dff` | `1024`, `4096` | Transformer hidden and feed-forward dimensions. |
| `--head`, `--kvhead` | `16`, `4` | Attention and key/value head counts. |
| `--num_stacks` | `2` | Two transformer blocks. |
| `--dvocal` | `32000` | Vocabulary size, the STAGE default at generation time. |
| `--mixed_precision` | `1` | STAGE's mixed-precision path; this revision selects its Llama-style dense graph. |
| `--weight_sharded`, `--activation_recompute` | `0`, `0` | Disabled. |
| `--tpsp` | `1` | STAGE default for the tensor/sequence parallel graph. |
| `--chakra_schema_version` | `v0.0.4` | Chakra trace schema. |

The parallel degrees multiply to `8 × 4 × 1 × 1 × 1 = 32` ranks. This is a small controlled workload for topology comparison, not a full-size production model.

The earlier `dense32` pilot used `--micro_batch 4`. STAGE first creates `Batch/MicroBatch` microbatches, then divides each dense microbatch among the eight DP replicas. That pilot therefore encoded **0.5 sequence per replica per microbatch**. Use the `dense32_validmb` files in this archive for the baseline.

## Regenerate with STAGE and Docker

Requirements: Git, Docker with the WSL distribution integrated (if using WSL), and enough disk space for the image and trace files. The commands use `~/astra-trace-work` as an example workspace; any writable directory works. No existing `cs6250` directory is required.

```bash
mkdir -p "$HOME/astra-trace-work"
cd "$HOME/astra-trace-work"
git clone https://github.com/astra-sim/stage.git stage
git -C stage checkout 71ceb42394bde658f9d4fd646168e42310c6a24d

docker build \
  --build-arg REPO_COMMIT=71ceb42394bde658f9d4fd646168e42310c6a24d \
  --build-arg HOST_UID="$(id -u)" --build-arg HOST_GID="$(id -g)" \
  -t stage-dense-baseline ./stage

docker run --rm -v "$PWD:/work" -w /work/stage \
  --entrypoint python stage-dense-baseline main.py \
  --output_dir /work/generated --output_name dense32_validmb \
  --model_type dense --dp 8 --tp 4 --ep 1 --pp 1 --sp 1 \
  --batch 32 --micro_batch 8 --seq 512 \
  --dmodel 1024 --dff 4096 --head 16 --kvhead 4 \
  --num_stacks 2 --dvocal 32000 --mixed_precision 1 \
  --weight_sharded 0 --activation_recompute 0 --tpsp 1 \
  --chakra_schema_version v0.0.4
```

STAGE's Dockerfile clones a revision into the image to install dependencies; the `REPO_COMMIT` build argument pins that copy. The mounted `stage` checkout used at run time must be at the same commit. The Python requirements in this STAGE revision do not pin package versions, so sharing the included `.et` and `.json` files is the reliable way to guarantee identical simulator inputs.

Check the regenerated files:

```bash
find generated -maxdepth 1 -name 'dense32_validmb.*.et' | wc -l
ls generated/dense32_validmb.json
```

The first command should print `32`. If you have this archive extracted beside `generated`, you can compare hashes from inside `generated`:

```bash
cd generated
sha256sum -c ../dense-baseline/SHA256SUMS
```

Replace `../dense-baseline` with the actual path to the extracted archive. A hash mismatch means the regenerated bytes differ; check the STAGE commit and Python package versions, or use the included canonical trace files for group experiments.

## Use with ASTRA-sim

Pass the trace **prefix** and its communicator file to ASTRA-sim:

```text
--workload-configuration=/absolute/path/to/dense32_validmb
--comm-group-configuration=/absolute/path/to/dense32_validmb.json
```

Do not include `.0.et` in the workload prefix; ASTRA-sim opens the rank files itself. Each topology experiment also needs its own network configuration, a matching system configuration, and the same simulator settings. For reproducible simulator runs, the ASTRA-sim checkout used in our smoke test was `4ce9ecfe746a3ee5fe47559a11d91644d641fa7f` with its pinned submodules:

```bash
git clone https://github.com/astra-sim/astra-sim.git
git -C astra-sim checkout 4ce9ecfe746a3ee5fe47559a11d91644d641fa7f
git -C astra-sim submodule update --init --recursive
```

Follow the [ASTRA-sim repository](https://github.com/astra-sim/astra-sim) to build the network backend you will use. An analytical 4×8 torus smoke run of this dense trace completed on all 32 ranks with no critical errors and reported 12,854,831 simulated cycles per rank. That is a compatibility check, not a calibrated training time or an ns-3 fat-tree/torus comparison: the smoke system configuration gives STAGE compute nodes almost no duration.

## Why the MoE trace uses different parallel degrees

The dense trace has no experts, so `EP=1` and the 32 ranks are `DP=8 × TP=4`. The MoE trace uses **eight experts with top-2 routing**. To make each expert's traffic visible on separate expert-parallel coordinates while keeping 32 ranks, our MoE pilot uses `DP=1 × TP=4 × EP=8`. Each expert occupies four physical ranks, one for each TP shard. Its global batch remains 32; with `DP=1`, `--micro_batch 4` represents four sequences per replica per microbatch and eight microbatches.

The dense and MoE traces share sequence length, model width, FFN width, head counts, and two blocks. Their parallel decomposition and microbatch count differ, so a dense-versus-MoE wall-time difference cannot be attributed only to expert routing. For topology evaluation, run **the same trace** on fat-tree and torus. For routing-skew evaluation, compare balanced and skewed MoE traces generated with the **same** MoE parallel degrees. STAGE's default MoE all-to-all traffic is uniform; the measured-skew variant requires a separate routing transformation and is not included in this dense-baseline archive.
